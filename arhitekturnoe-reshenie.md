## 1. Что меняется относительно ТЗ

### 1.1. Модель ценообразования (новое требование)

| Параметр | Было в ТЗ | Стало |
|---|---|---|
| Цена запроса | Фиксированная, 2,00 € | **Устанавливает заведение** в настройках клуба/сессии |
| Сплит | 1,00 / 0,50 / 0,50 € | **DROP IT получает комиссию** с каждого запроса |
| Остаток | — | Распределяется между клубом и диджеем |

**Модель (гибкая, настраивается per-club):**

```
Цена запроса P — задаёт клуб (минимум/максимум ограничены платформой)
Комиссия DROP IT C — процент или фикс (правила платформы, по клубам)
Остаток R = P − C − fee(платёжного провайдера)
R распределяется между клубом и диджеем по доле, заданной клубом (default 50/50)
```

Пример: клуб ставит 3,00 €; комиссия DROP IT 15 % (0,45 €); fee провайдера ~0,12 €; остаток 2,43 € → клуб 1,22 €, диджей 1,22 € (округление в пользу получателей, остаток цента — в комиссию платформы).

**Следствия для архитектуры:**
- Комиссия и доли — **конфигурация, а не код**: справочник тарифов клуба, версия тарифа фиксируется в каждом платёже (нельзя менять постфактум).
- Мин. цена, макс. цена, мин. комиссия — валидация на API и в админке.
- Финансовый модуль должен уметь считать сплит с точностью до цента, с audit trail каждой версии тарифа.

### 1.2. Технологическое решение

| Параметр | Было в КП | Стало |
|---|---|---|
| Бекенд | Node.js (NestJS) | **Rust** |
| Обоснование | Скорость разработки | Безотказность, нагрузка, детерминированная память, предсказуемый latency |

Честная оценка Rust (для заказчика):

| Плюс | Риск |
|---|---|
| Latency p99 в единицах миллисекунд; один узел держит десятки тысяч WS-соединений | Разработка на 20–30 % дольше, чем на Node — закладываем в сроки |
| Отсутствие GC-пауз → предсказуемая «безотказность» под пиковыми нагрузками пятничного вечера | Меньше готовых «коробок» — больше самостоятельного кода |
| Типобезопасность `Result`/типы состояний → большинство аварийных багов ловится компилятором | Найм дороже;.bus-factor — минимум 2 Rust-разработчика в команде |
| Один бинарник ~20–50 МБ, деплой прост, memory footprint в разы ниже JVM/Node | — |

Веб-панели остаются на **React + TypeScript** (это фронтенд, Rust там не нужен). Мобильные приложения — Flutter. Rust — бекенд и realtime-шлюз.

## 2. Ключевые требования к системе

| Требование | Целевое значение |
|---|---|
| Доступность API | 99,9 % (≤ 8,8 ч простоя/год), цель — 99,95 % |
| Отказ узла | Пользователь этого **не замечает**: WS-переподключение < 2 с, сессии сохранены |
| Деградация внешнего сервиса (Stripe / каталог) | Основной сценарий продолжает работать; «страница оплата недоступна», но поиск/просмотр живы |
| Пик нагрузки | Ночь пятницы: всплеск ×10 от среднего. Целевая расчётная ёмкость — 1000 клубов одновременно, 50 запросов/сек пик |
| Финансовый цикл | Полный: оплата → сплит → накопление → выплата → сверка. Ноль «подвешенных» денег |
| Потеря платежа | Невозможна by design: outbox + идемпотентность + сверка (reconciliation) |

### 2.1. Расчёт нагрузки (MVP → масштаб)

| Метрика | MVP (пилот) | Через год |
|---|---|---|
| Одновременных сессий (клубов) | 10 | 1000 |
| Активных посетителей в вечер | 200 | 20 000 |
| WS-соединений | 300 | 25 000 |
| Платежей в час (пик) | 100 | 5000 (~1,4/с) |
| Поисковых запросов к каталогу | 1000/час | 100 000/час (кэш снимает 80 %) |

Архитектура проектируется сразу под правую колонку, разворачивается под левую (те же контейнеры, меньше реплик).

  │  ┌──────────────────────────────────────────────────┴─────────────┘   │
  │  │ Нотификации · Антифрод · Аудит                                     │
  │  └───────────────────────────────────────────────────────────────────┘
  │                        OUTBOX → NATS JetStream                        │
  └──────────┬──────────────────────┬──────────────────────┬─────────────┘
             ▼                      ▼                      ▼
      ┌────────────┐        ┌────────────┐         ┌──────────────┐
      │ PostgreSQL │        │   Redis    │         │ S3-совмести- │
      │ primary +  │        │ кэш,       │         │ мое (логи,   │

**Разделение gateway / core / ws** — с первого дня это три процесса из одной кодовой базы (workspace cargo). Это даёт:
- независимое масштабирование (WS-шлюз ждёт пика пятницы, core — нет);
- изоляцию отказов: падение WS не роняет платежи;
- простой путь к выносу модулей в сервисы без переписывания.

## 4. Компоненты и решения

### 4.1. Стек Rust

| Компонент | Выбор | Почему |
|---|---|---|
| HTTP-фреймворк | **axum** | Экосистема tokio, tower (retry, timeout, load-shedding из коробки), типизация |
| Async runtime | **tokio** | Стандарт де-факто, work-stealing, метрики |
| БД-доступ | **sqlx** | SQL-first, compile-time проверка запросов, пулы |
| Миграции | **sqlx migrate** | Версионированные схемы |
| WS | axum + tokio | Долгоживущие соединения, heartbeat |
| Шина событий | **NATS JetStream** | Персистентные события, at-least-once, дёшево в эксплуатации; Kafka — избыточен для MVP |
| Конфиг | figment/env | 12-factor |
| Метрики/трейсинг | OpenTelemetry + Prometheus + Grafana; Grafana Loki для логов | Один стек наблюдаемости |
| Сериализация | serde + validator | Строгие границы входа |

### 4.2. Модель данных (ядро)

```
club (id, profile, payout_account_id, …)
  pricing_policy (id, club_id, min_price, max_price, valid_from)      ← версии тарифов клуба
  dj (id, club_id…, payout_account_id)
  session (id, club_id, dj_id, status, pricing_snapshot_id, opened_at, closed_at)
    qr (id, session_id, token_hash, active, expires_at)               ← QR перегенерируется на сессию
    request (id, session_id, track_isrc, title, artist, style, price_minor, status, created_at)
      payment (id, request_id, stripe_pi_id, idem_key, amount, status, split_snapshot jsonb)
        split (payment_id, payee_type, payee_id, amount_minor, status)
ledger_entry (двойная запись: каждый платёж и каждая выплата — проводки)
payout (id, payee_type, payee_id, period, amount, stripe_transfer_id, status)
reconciliation_run (id, period, stripe_report_id, matched, discrepancies)
audit_log (actor, action, entity, diff, at) — append-only
```

- Все суммы — **integer в минорных единицах** (центы). Никаких float.
- `pricing_snapshot` / `split_snapshot` — снимок правил на момент оплаты; изменение тарифа не влияет на уже оплаченные запросы.
- Статусы запроса — enum в Rust (`Pending → Accepted → Rejected → Played → Expired`), невозможные переходы не компилируются.

### 4.3. Полный цикл закрытия денег (требование «полный цикл»)

Каждый евро проходит 6 состояний, и все они наблюдаемы:

```
1. INTENT      гость подтвердил → payment: Pending, request: Pending
2. CAPTURED    Stripe подтвердил платёж (webhook, верифицированный подписью)
               → outbox: PaymentCaptured
3. LEDGERED    процессор-воркер записывает двойную проводку:
               revenue:DROP-IT / payable:клуб / payable:диджей
4. REQUEST_LIFECYCLE  диджей: принять / отклонить / проиграть
               (деньги уже закрыты — жизненный цикл запроса не блокирует финансы)
5. PAYOUT      по расписанию (еженедельно) или по кнопке (Instant):
               pending → transfer → paid; неуспех → retry с backoff → ручной разбор
6. RECONCILIATION  суточный/недельный автосверка со Stripe-отчётами:
               расхождения → incident в админку → ручное закрытие
```

**Правила целостности:**
- Проводка ledger и запись payment — **одна транзакция БД + outbox** (классический transactional outbox): событие о деньгах физически не может потеряться.
- Все обработчики — **идемпотентны** по `(id, event_type)`: повторная доставка NATS безопасна.
- Webhooks Stripe: верификация подписи, обработка строго идемпотентно по `event.id`, неизвестные события — в лог, не в ошибку.
- Инвариант, проверяемый nightly-джобом: `Σ payable = Σ un-paided payouts + Σ paid payouts` — расхождение блокирует выплаты и будит дежурного.

### 4.4. Безотказность (требование «безотказная»)

| Отказ | Поведение системы |
|---|---|
| Узел API упал | За LB (Cloudflare/внутренний) N≥2 узлов; клиенты ретраят идемпотентно |
| Узел WS упал | Клиент автопереподключается (< 2 c), состояние сессии — в Redis; запросы не теряются (источник истины — БД, WS только уведомляет) |
| PostgreSQL primary упал | Patroni + автоматический failover на реплику (RPO≈0 sync-реплика, RTO 10–30 с); API возвращает 503 + Retry-After на запись, чтение продолжает с реплик |
| Redis упал | WS-хаб деградирует до poll (запросы диджей получает с задержкой 5 с), платежи НЕ затрагиваются |
| NATS упал | Outbox-таблица накапливает события; воркеры досылают после восстановления; лимит/ретеншн контролируется алертом |
| Stripe недоступен | Каталог и всё остальное живут; экран оплаты: «повторить позже»; уже оплаченные деньги — в цикле закрытия, не потеряются |
| Каталог (iTunes) недоступен | Кэш Redis + ранее найденные треки; поиск новых — сообщение о недоступности |
| Зависание воркера | Watchdog (liveness в NATS), перезапуск контейнера; задачи в очереди переживают рестарт |

Принципы:
- **Состояние — только в Postgres/NATS. Процессы — stateless** (кроме WS-соединений, чей loss переживаем).
- **Circuit breaker на каждый внешний вызов** (tower + retry с jitter).
- **Graceful shutdown**: SIGTERM → дренаж соединений (60 с) → выход; деплой без разрыва.
- Всё, что стоит за деньгами, — **at-least-once + идемпотентность**, а не exactly-once.

### 4.5. Оптимизация под нагрузку

**API (Rust/axum):**
- Stateless-узлы за балансировщиком; горизонталим по CPU
- p99 бюджет: API ≤ 50 мс внутренний, ≤ 200 мс с внешними вызовами
- Тяжёлые отчёты клубов — read-реплика + materialized view, обновление каждые 5 мин

**WS-шлюз:**
- Один процесс Rust держит 30–50k соединений (tokio) → 25k соединений = 2–3 узла с запасом
- Shard по `session_id`: события сессии публиковать только на нужные узлы (consistent hashing по session)
- Heartbeat 15 с, dead-connection cleanup
- При 1000+ клубов: WS-шлюз отдельно от API, свой пул

**Каталог:**
- Redis-кэш по нормализованному `query+market`: hit-rate ~80 %, TTL 24 ч
- Rate-limit к iTunes с нашего бекенда;debounce поиска в клиенте (300 мс)

**Postgres:**
- Индексы `(session_id, status)`, `(payment_id)`, партиционирование `audit_log` и `ledger_entry` по месяцам
- Connection pool per-сервис, лимит на запрос
- Чтение статистики — реплики

**Плата за нагрузку — кубиками, а не преждевременной оптимизацией:** микросервисы НЕ заводим на старте. Монолит Rust с внутренними модулями переживёт 10–50k RPS; вынос модулей — по метрикам, когда появится реальная потребность.

### 4.6. Безопасность

- TLS 1.3 везде; HSTS; карта данные только в Stripe (токенизация, PCI DSS на их стороне)
- JWT (короткий, 15 мин) + refresh-токены; гость — device-token, без ПД
- RBAC 4 ролей; 2FA (TOTP) для диджей/клуб/админ
- QR-токен: случайный 128-бит, хранится hash; ротация на сессию; TTL — до конца ночи
- Rate limiting: на скан QR (10/мин/устройство), на поиск (30/мин), на платёжные интенты (5/мин/устройство)
- Антифрод: лимиты запросов с устройства за вечер, скоринг паттернов, Stripe Radar
- Секреты — в защищённом хранилище (Vault/SOPS), CI/CD без секретов в репозитории
- Аудит-лог append-only на все административные и финансовые действия

## 7. Открытые вопросы

1. **Комиссия DROP IT** — фикс с запроса или процент? единая для всех или per-club? (в модели заложено всё)
2. **Мин/макс цена** для клуба (валидация платформы) — предлагаю 1–10 €
3. **Доля диджея в остатке** — задаёт клуб или фикс платформы (например, 50 %)?
4. **Возврат при отклонении** — влияет на цикл закрытия: либо возврат в том же cycle (статус `Refunded` в ledger), либо «деньги закрыты» сразу. Рекомендация: без возврата, условия видны до оплаты; технически возврат заложен.
5. Команда: подтверждаем наличие 2 Rust-разработчиков (bus-factor).

## 8. Риски и меры

| Риск | Мера |
|---|---|
| Сроки съезжают из-за Rust | Модули платежей и WS — Rust с первого дня; нестандартное (отчёты, интеграции) — можно докладывать на JS/TS сервисами-сателлитами при необходимости |

| Рост каталогных API-лимитов | Кэш + debounce; при необходимости провайдер с квотами (Deezer) |
