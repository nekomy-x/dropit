# 4. Дизайн и прототип экранов

## 4.1. Визуальная идентичность (по ТЗ, раздел 10)

- Чёрный фон, белый текст, **неоново-зелёный** акцент
- Логотип — минималистичные наушники
- Современный «ночной» стиль: крупная типографика, контраст, атмосфера вечеринки и технологий
- Максимально простой интерфейс — весь сценарий от QR до оплаты укладывается в 4 шага

## 4.2. Перечень экранов (полный набор к прототипу)

**Посетитель (Flutter):**
1. Сканер QR-кода (быстрый запуск, запрос доступа к камере)
2. Экран вечеринки: DROP IT, диджей, стили вечера, кнопка «Найти песню»
3. Поиск с фильтром по стилям, список результатов с превью-кнопкой
4. Карточка песни: обложка, название, исполнитель, превью 30 сек, кнопка «Заказать — 2,00 €»
5. Экран условий перед оплатой: «Вы платите за отправку запроса, решение за диджеем», «повторные запросы оплачиваются отдельно»
6. Оплата: Apple Pay / Google Pay / карта
7. Успех: «Запрос отправлен диджею» + количество запросов этой песни

**Диджей (Flutter):**
8. Логин (пароль + 2FA)
9. Очередь запросов: песня, число запросов, время, стиль, сумма — крупно, читаемо «в темноте»
10. Карточка запроса: принять / отклонить / отметить как воспроизведённую
11. Переключатель стилей на вечер, кнопка «пауза приёма запросов»
12. Мини-статистика вечера

**Клуб (веб):**
13. Профиль клуба
14. Сессии: создать/редактировать/завершить
15. Привязка диджея к сессии
16. Генерация и активация QR-кода (перегенерируется на каждую сессию)
17. Доходы и статистика

**Админ DROP IT (веб):**
18. Дашборд: активные сессии, оборот, запросы
19. Клубы / диджеи / пользователи (просмотр, блокировка, приостановка)
20. Платежи и комиссии, разбор сплитов
21. Инциденты, антифрод-события, аудит-лог

## 4.3. Формат

- Интерактивный прототип в **Figma** (кликабельный, все 20+ экранов)
- Дизайн-система: цвета, типографика, компоненты, состояния кнопок, тёмная тема
- Прототип согласуется на 2-й неделе и является основой для приёмки визуала

# 5. Архитектура приложения

## 5.1. Ключевое решение

**Модульный монолит** на бекенде — правильный выбор для старта: проще разрабатывать за 3 месяца, дешевле поддерживать. Внутри чёткие модули (сессии, заказы, каталог, платежи, уведомления), что позволяет в будущем выносить их в отдельные сервисы без переписывания.

## 5.2. Схема

```
┌─────────────┐   ┌─────────────┐   ┌──────────────┐   ┌──────────────┐
│ Посетитель  │   │   Диджей    │   │ Клуб (веб)   │   │ Админ (веб)  │
│ Flutter     │   │   Flutter   │   │              │   │              │
└──────┬──────┘   └──────┬──────┘   └──────┬───────┘   └──────┬───────┘
       │  HTTPS/WSS      │  HTTPS/WSS      │   HTTPS          │   HTTPS
       ▼                 ▼                 ▼                 ▼
┌─────────────────────────────────────────────────────────────────────┐
│                 API Gateway (авторизация, роли, rate-limit)          │
├─────────────────────────────────────────────────────────────────────┤
│                      Backend (NestJS)                                │
│  ┌────────────┬──────────┬──────────┬───────────┬───────────────┐    │
│  │ Сессии/QR  │ Заказы   │ Каталог  │ Платежи   │ Уведомления   │    │
│  │ и роли     │          │          │ Stripe    │ + Realtime    │    │
│  └────────────┴──────────┴──────────┴───────────┴───────────────┘    │
├─────────────────────────────────────────────────────────────────────┤
│  PostgreSQL        Redis + BullMQ        WebSocket-хаб               │
└───────────────┬──────────────────────────────┬───────────────────────┘
                │                              │
        ┌───────▼────────┐            ┌─────────▼─────────┐
        │  Stripe Connect │            │ Музыкальный       │
        │  (платежи,      │            │ каталог           │
        │  сплит, KYC)    │            │ iTunes/Deezer/    │
        └────────────────┘            │ MusicBrainz       │
                                      └───────────────────┘
```

## 5.3. Ключевые механизмы

- **Роли и доступ**: 4 роли (гость, диджей, клуб, админ), RBAC, JWT + refresh-токены, 2FA для панелей диджея/клуба/админа
- **Гость без регистрации**: посетитель не создаёт аккаунт — сессия привязывается к QR-коду и устройству. Минимум персональных данных = минимум GDPR-обязательств
- **Реалтайм**: WebSocket-хаб доставляет запросы диджею за доли секунды; офлайн-режим дублируется push-уведомлениями
- **Финансовая целостность**: сплит платежа выполняется в одной транзакции (Stripe transfer_group), статусы платежей и запросов хранятся в Postgres с аудит-логом
- **Масштабирование**: валюты и языки — таблицы/словари, а не захардкоженные значения; инфраструктура готова к добавлению стран

# 6. Платёжная система

## 6.1. Рекомендация: Stripe Connect

Единственное коробочное решение, которое закрывает специфику DROP IT:

| Потребность DROP IT | Решение Stripe |
|---------------------|----------------|
| 2 € за запрос, распределение 1/0,50/0,50 | **Сплит-платежи** с одного платежа на 3 получателя (transfer_group) |
| Диджей и клуб — сами получатели | **Connect**: у каждого свой счёт, автовыплаты на банк |
| Проверка диджеев/клубов (KYC, санкции, антиотмывочные) | Встроенный онбординг и верификация, 46+ стран |
| Apple Pay / Google Pay / карты | Из коробки, без доп. интеграций |
| Мультивалютность и новые страны | 135+ валют, локальные платёжные методы |
| Антифрод | **Stripe Radar** + настраиваемые правила |
| Юридическая нагрузка в ЕС | У Stripe лицензии EMI — платежи «как платформа» легальны без собственной лицензии |

Альтернативы (Mollie, Adyen) рассматривались: Mollie дешевле в отдельных странах ЕС, но сплиты и KYC-онбординг менее развиты; Adyen — уровень enterprise с неподъёмным для старта порогом. Рекомендуем Stripe.

## 6.2. Финансовая математика одного запроса

Исходно: **2,00 €** за запрос.
Комиссия Stripe ≈ **2–3 % + фикс.** (зависит от страны карты; для ЕС-карт ниже).

Два варианта распределения (фиксируется с заказчиком):

| Вариант | DROP IT | Диджей | Клуб |
|---------|--------:|-------:|-----:|
| А. Комиссия из доли DROP IT | 2,00 − комиссия − 1,00 | 0,50 | 0,50 |
| Б. Пропорционально всем | ~0,94 | ~0,47 | ~0,47 |

Вариант А проще для коммуникации с клубами и диджеями («вы получаете ровно 0,50 € с запроса») — рекомендуем.

## 6.3. Организация выплат

- Диджей и клуб привязывают банковский счёт при онбординге (через Stripe)
- **Автоматические еженедельные выплаты** каждому получателю
- Клуб дополнительно может получить **Instant Payouts** (вывод по кнопке, за небольшую комиссию)
- В админке — полный разбор: сколько удержано, кому и когда перечислено

## 6.4. Важные юридические замечания

1. **Покупка заказа — это услуга реального мира**, а не цифровой контент, поэтому оплата через Stripe (Apple Pay/карта) напрямую допустима и **не требует** комиссии App Store IAP (аналогично заказу такси или еды). Apple Pay здесь — просто метод оплаты внутри Stripe.
2. **Налоги**: правила VAT/B2C зависят от страны клуба. На старте подключаем Stripe Tax для автоматического расчёта; финальную схему согласует бухгалтер заказчика.
3. **Открытый вопрос к заказчику**: что происходит с оплатой при **отклонении** запроса диджеем? Варианты: без возврата (по букве ТЗ — плата за отправку запроса) либо автовозврат (улучшает доверие пользователей). Рекомендуем обсудить.

# 7. Система управления музыкальным каталогом

## 7.1. Принципиальная схема

DROP IT **не воспроизводит** музыку: приложение проигрывает только 30-секундные превью, а полноценное воспроизведение остаётся на диджее из его лицензионной библиотеки. Это ключевой юридический факт, который сильно упрощает работу сервиса.

## 7.2. Источники каталога

| Источник | Что даёт | Лицензионный статус |
|----------|----------|---------------------|
| **iTunes Search API** (Apple) | Поиск по названию/исполнителю, метаданные, обложки, **30-сек превью** | Бесплатно, без ключа; превью лицензированы Apple |
| **Deezer API** | Резервный источник **30-сек превью**, сильный латинский каталог | Требует ключ и согласование |
| **MusicBrainz** | Серверное обогащение: ISRC, идентификаторы, правки | Открытые данные (CC0) |

> **Важно про Spotify:** с ноября 2024 Spotify прекратил отдавать 30-сек превью через Web API (`preview_url` = null). Поэтому Spotify как источник каталога не рассматривается — это стоит озвучить заказчику, если он предполагал Spotify.

## 7.3. Как это работает

1. Пользователь вводит название песни → поиск идёт через iTunes API **напрямую из приложения** (Apple блокирует серверные дата-центры; из клиента работает стабильно и без ключа)
2. Сервер дополняет результат через MusicBrainz: получает **ISRC-код** и точные идентификаторы
3. ISRC сохраняется в заказе → диджей получает карточку с названием, исполнителем, ISRC и может за секунды найти трек в своей программе (Rekordbox/Serato и др.)
4. Если у iTunes нет превью для редкого трека — подключается Deezer
5. Каталог-сервис кэширует запросы (Redis), чтобы не перегружать внешние API и ускорить повторный поиск

## 7.4. Лицензионная позиция (для раздела 5 ТЗ)

- Превью (30 сек) покрыты лицензиями провайдеров (Apple/Deezer) — **дополнительных лицензий DROP IT не покупает**
- Полное воспроизведение в клубе — ответственность клуба и диджея: клубы в ЕС обычно уже платят коллективным обществам (SACEM, GEMA, SGAE, PPL/PRS и т.д.)
- DROP IT юридически является платформой заказов, а не стриминговым сервисом
- Рекомендация: перед запуском в новой стране подтвердить позицию у локального юриста (30 минут консультации) — в смету не включено

# 8. Защита данных

## 8.1. Подход

Безопасность закладывается на уровне архитектуры (раздел 5), а не «допилкой в конце». Применяем стандарт **GDPR** как базовый — он самый строгий, и подготовка к нему автоматически закрывает требования большинства стран.

## 8.2. Меры защиты

**Данные и шифрование**
- Шифрование при передаче: TLS 1.3 везде
- Шифрование в покое: AES-256 для базы и бэкапов
- Хостинг в ЕС (Hetzner/AWS Frankfurt или аналоги), данные не покидают юрисдикцию без необходимости

**Платёжные данные — минимум**
- Карты НЕ хранятся у нас: платёжные данные уходят напрямую в Stripe (токенизация, PCI DSS на стороне Stripe)
- Мы храним только идентификаторы платежей и статусы

**Персональные данные — минимум**
- Посетитель — гость без регистрации: не собираем имя, почту, телефон. Только транзакционные данные (устройство, время, IP для антифрода)
- Диджеи и клубы: только то, что требуется для KYC/выплат (через Stripe) и работы сервиса
- Политика конфиденциальности и условия использования — обязательная часть публикации в сторах

**Доступ и контроль**
- RBAC: гость / диджей / клуб / админ, разграничение доступа к API
- JWT + refresh-токены, httpOnly-куки для веб-панелей
- 2FA для всех панелей (диджей, клуб, админ)
- Аудит-лог всех административных действий и финансовых операций

**Антифрод**
- Stripe Radar (машинное обучение + правила)
- Свои правила: лимиты на количество запросов с устройства в час/вечер, подозрительные паттерны повторных заказов, скоринг сессий

**Операционная безопасность**

- CI/CD с секретами в защищённом хранилище (не в репозитории)
- Мониторинг и оповещения, план реагирования на инциденты
- Обновление зависимостей с проверкой уязвимостей (Dependabot/Snyk)

# 9. Способ передачи исходного кода

## 9.1. Что передаётся (по разделу 14 ТЗ — полное владение заказчиком)

- Исходный код всех компонентов: мобильные приложения, бекенд, веб-панели, сайты
- Дизайн: исходники Figma, логотип, дизайн-система, все ассеты
- Документация: архитектура, README, гайд по развёртыванию, схема базы, инструкции для команд
- Инфраструктура: конфигурации, доступы, инструкции по деплою

## 9.2. Механика передачи

1. Репозиторий создаётся на **GitHub/GitLab под юрлицом заказчика** с самого старта; исполнитель получает доступ как разработчик
2. Доступы к инфраструктуре (хостинг, базы, Stripe, сторы) оформляются на аккаунт владельца, исполнитель — на правах администратора по договору
3. Передача финальная — по акту после полной оплаты; вся история коммитов, документация и ассеты остаются у владельца
4. Права: договор фиксирует **полную уступку исключительных прав** на код, дизайн, торговую марку и материалы DROP IT владельцу (без права использования исполнителем вне договора)

## 9.3. Сторы

Аккаунты App Store / Google Play оформляем и ведём мы; юридически они регистрируются на юрлицо владельца (требование Apple), с полной передачей доступа владельцу. При необходимости — процедура App Transfer.
