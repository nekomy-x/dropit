# ADR-008: Транзакционные письма через Resend (HTTP API)

**Статус:** реализовано
**Дата:** 2026-10-27
**Контракт:** `docs/mail-infra-contract.md`
**Связано:** ADR-002 (outbox/NATS), ADR-005 (WS — только уведомления)

## Контекст

Продукту нужны транзакционные письма: приглашение DJ в клуб (сейчас клуб
получает `invite_token` в ответе API и передаёт его вручную), подтверждение
e-mail гостя (колонка `guest_account.verified` заведена миграцией 0010, но
всегда `false` — «флоу верификации за рамками пакета»), уведомление о выплате.
До этой итерации в репозитории не было **ни одной** почтовой зависимости: ни
крейта, ни таблиц, ни переменных окружения.

Ограничения, которые определили решение:

- нельзя ломать деградацию: приложение обязано подниматься без почтовых ключей
  и оставаться работоспособным (как `MockStripe` / `NoopPush` / `NoopBus`);
- `deny.toml` банит GPL/AGPL и неизвестные реестры — новая зависимость должна
  быть чистой по лицензии и не тянуть транзитивно сомнительное;
- отправка не должна блокировать обработчик запроса: SMTP/HTTP-таймаут
  провайдера не имеет права задерживать ответ клубу или гостю;
- нужен аудит: «что, кому, когда отправили и что стало с письмом» — это
  операционный продукт, письма здесь такие же объекты наблюдения, как платежи.

## Решение

**Resend HTTP API как единственный транспорт** + собственный тонкий клиент.

1. **Крейт `crates/infra-mail`** (`dropit-infra-mail`) — по образцу
   `infra-push`: трейт `MailSender`, реализации `ResendSender` и `NoopMail`,
   внутренний `HttpTransport`, который в тестах подменяется фейком (сети в
   юнит-тестах нет). Никаких новых сторонних крейтов: `reqwest`, `hmac`,
   `sha2`, `base64`, `hex`, `chrono` уже в workspace.
2. **Очередь в Postgres, а не отправка в обработчике.** Таблица
   `mail_message` — это и есть очередь: `enqueue` пишет строку, воркер
   `dropit-workers` забирает её `SKIP LOCKED`-батчем и отправляет. Тот же
   приём, что у outbox (ADR-002), но с собственной таблицей: письмо имеет
   собственный жизненный цикл (attempts, backoff, provider_id), и смешивать
   его с outbox-событиями значило бы усложнить оба.
3. **Идемпотентность на двух уровнях.** `mail_message.idempotency_key`
   UNIQUE и одновременно значение заголовка `Idempotency-Key` для Resend
   (провайдер помнит ключ 24 ч): повторная бизнес-операция не создаёт второе
   письмо ни у нас, ни у провайдера. События вебхуков дедуплицируются по
   `svix-id`.
4. **Вебхуки — единственный источник истины о доставке.** `POST
   /webhooks/resend` проверяет Svix-подпись (HMAC-SHA256 над
   `"{svix_id}.{svix_timestamp}.{raw_body}"`, допуск 300 с) и только потом
   разбирает тело. Без `RESEND_WEBHOOK_SECRET` роут отвечает `503`, а не
   принимает неподписанное: «доставлено» — это утверждение о деньгах и
   доступе, ему нельзя верить на слово.
5. **Переходы состояния монотонны и проверяются в SQL.** Позднее `sent` не
   откатывает `delivered`; `bounced`/`complained` дополнительно пополняют
   `mail_suppression`, и диспетчер не отправляет на подавленные адреса.
6. **Шаблоны — в коде, без движка.** Четыре шаблона с `{{var}}`-подстановкой:
   движок шаблонов ради четырёх писем — это лишняя зависимость и лишняя
   поверхность атаки (SSTI), а редактирование шаблонов из БД не входило в
   задачу.

## Следствия

- Письма уходят с задержкой до `MAIL_INTERVAL_SECS` (по умолчанию 2 с) —
  для инвайтов и подтверждений это неощутимо, зато провайдерский таймаут
  никогда не попадает в latency API.
- Доставка at-least-once: падение между `send` и `mark_sent` приводит к
  повтору, который провайдер схлопывает по `Idempotency-Key`. Дубликат
  возможен только при смене ключа, то есть при осознанном `resend`.
- При недоступном провайдере письма копятся в `queued` с backoff
  `min(2^attempts · 5 с, 1 ч)`; после `MAIL_MAX_ATTEMPTS` строка становится
  `failed` и остаётся видимой в админке, но не блокирует очередь.
- Без ключей (`RESEND_API_KEY` пуст) работает `NoopMail`: строки журнала
  создаются, в сеть ничего не уходит, воркер печатает `noop` в отчёте. Это
  позволяет прогонять e2e и демо-стенд без почтового аккаунта.
- Репутация домена — операционная ответственность: bounce/complaint видны в
  `/v1/admin/mail/stats`, подавления снимаются вручную после разбора.

## Альтернативы

- **SMTP через `lettre`.** Универсальнее (любой ESP), но тянет крупную
  зависимость с TLS-стеком, и у нас не было ни одного SMTP-потребителя.
  Отложено: трейт `MailSender` позволяет добавить SMTP-реализацию, не меняя
  ни БД, ни воркер, ни API.
- **Отправка прямо в обработчике (`tokio::spawn`).** Проще, но теряет письма
  при рестарте процесса и не даёт ни retry, ни журнала — противоречит
  ADR-002.
- **SendGrid/Postmark/SES.** Сопоставимы по возможностям; выбрали Resend за
  простой HTTP-контракт, идемпотентность из коробки и Svix-подписи. Смена
  провайдера = новая реализация `MailSender` + маппинг событий.
- **Шаблоны в БД с редактированием из админки.** Не нужно на этом этапе:
  письма системные, их текст меняется вместе с кодом и проходит ревью.

## Проверка

- `cargo test -p dropit-infra-mail` — транспорт, идемпотентность, маппинг
  ошибок, Svix (подделка/просрочка/несколько `v1`), разбор событий, шаблоны.
- `cargo test -p dropit-infra-db mail` — claim/backoff/подавления/keyset/
  монотонность переходов.
- `cargo test -p dropit-workers` — диспетчер на фейках.
- `cargo test -p dropit-gateway-api e2e_mail` — подписанный/неподписанный/
  дублирующий вебхук, админ-роуты, RBAC, автопостановка письма при инвайте DJ.
- `node scripts/panel-audit.mjs --app admin --route /admin/mail` — экран
  журнала в обеих темах.
